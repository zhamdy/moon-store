## The one change a code generator will notice

79 path parameters are redescribed from `{ type: 'integer' }` to
`{ type: 'string', pattern: '^\d+$' }`, plus four more specific cases:

| Count | From | To | Example |
| --- | --- | --- | --- |
| 79 | `integer` | `string` matching `^\d+$` | `PUT /api/v1/users/{id}` |
| 3 | `string` | `string`, 1-100 chars | `GET /api/v1/products/barcode/{barcode}` |
| 1 | `integer` | `string`, 1-255 chars | `DELETE /api/v1/reservations/source/{sourceId}` |

A generated client will type those arguments `string` where it previously typed `number`.
That is worth a deliberate decision rather than a shrug, so:

- A path parameter **is** a string on the wire. The old `integer` was a claim nobody
  enforced — nothing validated these at all, which is why `GET /api/v1/products/abc`
  returned a 404 or a 500 depending on the module rather than a 400.
- The new schema is *stricter* than the old one was in practice: `^\d+$` also rejects
  `-1` and `1.5`.
- Declaring `integer` while validating a string would reintroduce exactly the gap this
  change closes — a documented shape the validator disagrees with.
- `sourceId` was documented as an `integer` and is a client-minted correlation string.
  That was a documentation bug; the derivation found it.

The alternative is to coerce path ids to numbers at the boundary so they document as
`integer` honestly. That changes what every controller receives and is a larger, separate
change.
